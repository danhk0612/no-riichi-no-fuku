# No Riichi No Fuku - Work 개발 지침

이 문서는 새 ChatGPT Work 또는 다른 개발 에이전트가 이 저장소에서 작업할 때 따라야 하는 프로젝트 기준이다.

## 1. 작업 시작 순서

매 작업 시작 시 다음 순서로 확인한다.

1. `AGENTS.md`
2. `README.md`
3. `docs/PROJECT_PLAN.md`
4. `docs/DECISIONS.md`
5. `docs/WORK_START.md`
6. 현재 코드와 테스트
7. 현재 Git 상태와 최근 변경사항

저장소의 현재 구현을 우선하며, 오래된 대화나 추측으로 기존 코드를 덮어쓰지 않는다.

## 2. 변경 원칙

- 사용자가 요청한 범위만 변경한다.
- 요청되지 않은 기능, 추상화, UI 재설계, 의존성 변경을 임의로 추가하지 않는다.
- 요구사항과 기존 구조가 충돌하면 충돌 지점을 명확히 보고한다.
- 수정이 필요한 파일을 먼저 확인한 뒤 최소 범위로 변경한다.
- 대규모 리팩터링은 별도 지시 없이는 수행하지 않는다.
- 새 기능을 만들기 위해 기존 동작을 제거하지 않는다.

## 3. GitHub를 기준정보로 사용

- GitHub 저장소를 프로젝트의 source of truth로 사용한다.
- 중요한 설계 변경은 문서와 코드가 함께 갱신되어야 한다.
- 작업 브랜치는 기능 단위로 분리한다.
- 완료 전에 diff와 테스트 결과를 확인한다.
- 직접 관련 없는 파일은 한 커밋에 섞지 않는다.

권장 브랜치 예:

```text
feat/auth
feat/admin-cpu
feat/mahjong-engine
feat/cpu-tier-0
fix/game-result
```

## 4. 라이선스

현재 자체 코드는 MIT License를 기준으로 한다.

오픈소스를 새로 도입할 때 반드시 라이선스를 확인한다.

- MIT / BSD / Apache 계열: 조건과 NOTICE 요구사항 확인 후 사용 가능
- GPL / AGPL 계열: 사용 자체를 금지하지 않는다.
- GPL/AGPL 코드를 프로젝트에 결합해야 한다면 해당 변경과 동시에 프로젝트 전체 라이선스 호환성을 검토하고 필요한 경우 프로젝트를 GPL/AGPL 계열로 전환한다.
- 라이선스가 불명확하거나 비상업 전용/재배포 제한인 코드는 임의로 사용하지 않는다.

현재 1차 마작 엔진 후보는 Apache-2.0의 RiichiEnv 0.4.8이다.

## 5. CG 및 미디어

- CG 이미지 파일을 Git 저장소에 생성하거나 커밋하지 않는다.
- 더미 CG도 저장소에 넣지 않는다.
- CG는 런타임 관리자 업로드로만 추가한다.
- 프로필 이미지와 CG는 Docker persistent media volume에 저장한다.
- DB에는 파일 키와 메타데이터만 기록한다.
- 테스트에서 실제 CG가 필요하면 바이너리 대신 fixture용 메타데이터를 사용한다.

## 6. 캐릭터 기준

- CPU 캐릭터는 모두 명시적으로 성인 캐릭터로 취급한다.
- 캐릭터 자체 데이터와 사용자별 진행 데이터를 분리한다.
- `defeat_stage`는 0~3이다.
- stage 3은 최종 완료이며 선택할 수 없다.
- stage 0/1/2는 각각 CPU Tier 0/1/2를 사용한다.
- 캐릭터 성향과 CPU 난이도를 하나의 값으로 합치지 않는다.

## 7. 마작 게임 규칙

- 4인 일본 리치마작
- 동풍전
- 사람 1명 + CPU 3명
- 현재 초기 가정은 RiichiEnv `4p-red-east` + Tenhou 계열 기본 규칙
- 실제 RiichiEnv 0.4.8 API와 세부 룰은 첫 통합 스파이크에서 확인한다.
- 세부 룰을 사용자 승인 없이 임의 변경하지 않는다.
- 게임의 최종 권한은 서버에 둔다.
- 클라이언트는 서버가 제공한 합법 행동 후보와 자신의 정보만 표시하고 행동 요청을 전송한다.

## 8. 결과 처리

동풍전 최종 순위만으로 진행 상태를 바꾼다.

### CPU가 4위

```text
cpu_progress.defeat_stage += 1
```

- stage 1/2/3 결과 화면 사용
- 해당 단계 결과 대사 출력
- 다음 대국부터 상승한 난이도 적용
- stage 3이면 선택 불가

### 플레이어가 4위

```text
current_hp -= 1
```

- CPU 진행도는 변하지 않음
- HP가 0이면 게임 오버

## 9. CPU 구현 원칙

외부 LLM/API를 마작 의사결정에 사용하지 않는다.

공통 인터페이스를 둔다.

```python
class MahjongAgent:
    def choose_action(self, observation):
        ...
```

### Tier 0

- 샹텐 우선
- 기본 유효패
- 약한 수비
- 상위 합리적 후보 중 가중 선택

### Tier 1

- 패효율
- 타점/도라
- 기본 수비
- 기본 push/fold

### Tier 2

- 고급 안전도
- 공수 기대값
- 남은 순목
- 현재 점수/순위
- 동4국 조건

Mortal 같은 모델을 추가하더라도 `MahjongAgent` 어댑터 뒤에 연결하고 게임 엔진과 UI가 특정 AI 구현에 의존하지 않도록 한다.

## 10. CPU 튜닝 원칙

- Easy를 단순 무작위 CPU로 만들지 않는다.
- 명백한 최악 수를 의도적으로 자주 고르는 방식으로 난이도를 낮추지 않는다.
- 난이도는 평가 정보량, 후보 선택 폭, 위험도 판단 정확도 차이로 만든다.
- 캐릭터 성향이 난이도 상승으로 사라지지 않게 한다.
- 변경 후 자동 시뮬레이션으로 Tier 간 상대 성능을 확인한다.

## 11. 최고 관리자

초기 최고 관리자 ID/암호는 코드나 저장소에 하드코딩하지 않는다.

환경변수:

```text
SUPERADMIN_LOGIN_ID
SUPERADMIN_INITIAL_PASSWORD
```

필수 동작:

- 최초 생성 시 `must_change_password = true`
- 비밀번호 변경 전 일반 관리자 기능 접근 제한
- 변경 후 초기 환경변수 값으로 재설정하지 않음

최고 관리자 초기 범위:

- 회원 관리
- CPU 관리
- CPU 성향 관리
- 대사 관리
- CG 관리
- 게임 기본 설정

## 12. Docker 원칙

초기 서비스는 다음 3개만 유지한다.

```text
web
api
db
```

영속 볼륨:

```text
postgres_data
media_data
```

요구가 생기기 전 Redis, Kafka, MinIO 등 별도 인프라를 추가하지 않는다.

실제 Docker/Compose 빌드와 통합 실행 검증은 최종 통합 단계에서 수행한다. 개발 중에는
Docker 골격을 불필요하게 확장하지 않고 백엔드/프론트엔드를 직접 실행해 관련 기능을
검증한다.

## 13. 보안 기본선

- 비밀번호 평문 저장 금지
- 저장소에 실제 비밀번호/토큰/비밀키 커밋 금지
- 업로드 파일은 서버가 지정한 저장 키로 보관
- 관리자 API는 서버 측 권한 확인 필수
- 클라이언트가 보낸 순위/점수/HP/진행도 값을 신뢰하지 않음

## 14. 완료 보고

각 작업 완료 시 다음만 간단히 보고한다.

- 변경한 기능
- 주요 변경 파일
- 실행한 테스트
- 테스트할 수 없었던 부분
- 사용자 확인이 필요한 미확정 사항

## 15. 하지 말아야 할 것

- CG 생성 또는 CG 파일 커밋
- 외부 AI API를 임의 도입
- 마작 규칙을 프론트엔드에서 최종 판정
- CPU마다 별도 게임 엔진 작성
- 사용자별 CPU 진행도를 CPU 마스터 테이블에 저장
- 최고 관리자 초기 비밀번호를 소스에 작성
- 사용자가 요청하지 않은 과금/멀티플레이/랭킹 시스템 추가
